# Мониторинг ML-сервиса

Сервис читает транзакции из Kafka, рассчитывает скор и флаг фрода, затем сохраняет результаты в PostgreSQL. Генератор непрерывно создаёт новые транзакции с частотой ~ 10 транз/сек. Модель работает на CPU.

Prometheus собирает метрики скоринга, записи результатов и Node Exporter раз в секунду. Все сервисы запускаются через Docker Compose в одной сети.

## Запуск

Нужен Docker с Compose v2.

```bash
docker compose up -d --build
docker compose ps -a
```

Контейнеры kafka-init и model-init должны завершиться с кодом 0. Остальные сервисы остаются запущенными. 

Grafana: http://localhost:3000

Логин: admin. Пароль: fraud_monitoring.

Prometheus: http://localhost:9090

Проверка сбора метрик: http://localhost:9090/targets. Цели scorer, writer и node должны быть в состоянии UP.

Источники Prometheus и PostgreSQL, дашборды и алерты подключаются автоматически. Файлы настройки находятся в grafana/provisioning, дашборды — в grafana/dashboards, конфигурация Prometheus — в prometheus/prometheus.yml.

## Дашборды

### 01 · Скоринг потока

http://localhost:3000/d/fraud-scoring

Скорость обработки транзакций, время обработки p95, доля фрода, распределение скоров во времени, возраст события и смена версии модели.

В верхнем ряду рядом со скоростью и временем обработки из Prometheus расположена таблица PostgreSQL «Скоры и доля фрода по версии модели». Она показывает число скоров, долю фрода в процентах и средний скор каждой версии за выбранный период для всего потока. На одном экране видно, что обработка идёт и какие результаты даёт каждая версия модели.

### 02 · Запись результатов

http://localhost:3000/d/fraud-writer

Скорость и время записи в PostgreSQL, число транзакций с флагом фрода, распределение записанных скоров, ошибки и повторные доставки.

### 03 · Ресурсы среды

http://localhost:3000/d/fraud-system

Загрузка CPU, использование памяти, сетевой трафик, чтение и запись диска, заполнение файловых систем. В Docker Desktop это ресурсы Linux VM, в которой работают контейнеры.

### 04 · Сегменты и бизнес

http://localhost:3000/d/fraud-business

Данные берутся из PostgreSQL. Таблица показывает количество скоров и долю фрода по версии модели.

Фильтры Штат (us_state) и Мерчант (merch) применяются к плотности распределения скоров и TPS. Можно выбрать одно значение, несколько или All. Для проверки выберите CA и market, затем сравните графики с All.

Плотность считается по интервалам скоров шириной 0.05 с нормировкой на размер выборки. TPS — число обработанных транзакций за полный десятисекундный интервал, делённое на 10.

График по cat_id показывает среднюю долю фрода в последних 1000 транзакций всего потока. Он не зависит от фильтров и выбранного периода. Если строк пока меньше 1000, используются все имеющиеся.

Дополнительный график показывает сумму подозрительных транзакций по мерчантам. Он помогает выбрать, какие операции проверять в первую очередь по денежному объёму. Это сумма помеченных покупок, а не подтверждённый ущерб.

## Метрики

Метрики скоринга доступны по адресу http://localhost:8000/metrics.

fraud_processed_total — число обработанных транзакций.

fraud_processing_seconds — время обработки одной транзакции.

fraud_score — гистограмма скоров.

fraud_flagged_total — число транзакций с флагом фрода.

fraud_ratio — доля фрода с запуска процесса. На дашборде доля за последнюю минуту рассчитывается по счётчикам.

fraud_event_age_seconds — время от создания транзакции до публикации скора.

fraud_last_processed_timestamp_seconds — время последнего обработанного сообщения.

fraud_errors_total{stage} — ошибки проверки сообщения и загрузки модели.

fraud_model_updates_total{version} — число переключений на новую версию модели.

fraud_model_loaded_timestamp_seconds{version} — время загрузки новой версии.

fraud_model_active{version} — текущая активная версия модели.

Метрика fraud_event_age_seconds добавлена относительно примера семинара. Она показывает задержку доставки и ожидания в очереди, которую нельзя увидеть только по времени вычисления скора. Её можно посмотреть на панели «Возраст события · p95» первого дашборда.

Метрики записи доступны по адресу http://localhost:8001/metrics.

writer_scores_total — число новых скоров, записанных в PostgreSQL.

writer_write_seconds — время записи.

writer_fraud_total — число записанных транзакций с флагом фрода.

writer_score — гистограмма записанных скоров.

writer_duplicates_total — число повторных доставок уже записанных результатов.

writer_errors_total — ошибки записи.

Node Exporter отдаёт системные метрики: node_cpu_seconds_total, node_memory_*, node_network_*, node_disk_* и node_filesystem_*.

Гистограммы публикуют серии с суффиксами _bucket, _sum и _count.

## Проверка потока

Откройте страницу метрик скоринга и обновите её через несколько секунд. Значение fraud_processed_total должно увеличиться. На странице метрик записи должен расти writer_scores_total.

В Prometheus выполните запрос:

```promql
rate(fraud_processed_total[30s])
```

Пока генератор работает, скорость должна быть больше нуля. В Grafana выберите период Last 15 minutes и проверьте данные на первых трёх дашбордах.

## Проверка смены модели

Откройте первый дашборд и запустите переобучение:

```bash
docker compose run --rm trainer
```

Новая модель публикуется в общем томе. Скоринг подхватывает её без перезапуска контейнера и увеличивает fraud_model_updates_total с меткой новой версии.

На дашборде появится отметка с версией модели. На панели переключения модели сигнал держится около 30 секунд. В таблицах первого и четвёртого дашбордов появится строка новой версии с количеством скоров и долей фрода.

Загрузку можно проверить в логах:

```bash
docker compose logs --since 2m scorer
```

## Проверка алертов

Правила находятся в grafana/provisioning/alerting/rules.json и загружаются при запуске. Смотреть их можно в разделе Alerting: http://localhost:3000/alerting/list. Проверка условий выполняется раз в 10 секунд. Доставка уведомлений не настроена.

### Высокая доля фрода

Алерт срабатывает, если доля помеченных транзакций за последнюю минуту выше 35% и условие сохраняется 30 секунд.

```bash
docker compose exec generator python -m app.scenario fraud
```

Генератор начнёт создавать рискованные транзакции. Примерно через 60–100 секунд алерт должен перейти в состояние Firing.

Верните обычный поток:

```bash
docker compose exec generator python -m app.scenario normal
```

Примерно через 60–90 секунд алерт вернётся в Normal.

### Поток остановился

Алерт срабатывает, если после последнего обработанного сообщения прошло больше 20 секунд и это условие держится ещё 20 секунд.

```bash
docker compose exec generator python -m app.scenario paused
```

После обработки оставшихся сообщений примерно через 40–60 секунд появится состояние Firing.

Возобновите поток:

```bash
docker compose exec generator python -m app.scenario normal
```

После новых обработанных сообщений алерт вернётся в Normal.

## Автоматические проверки

После запуска подождите около минуты для накопления данных и выполните:

```bash
docker compose exec -T scorer python -m unittest discover -s tests -v
docker compose exec -T scorer python scripts/smoke.py
docker compose exec -T scorer python scripts/check_dashboards.py
```

Проверки подтверждают работу модели, рост счётчика на живом потоке, доступность трёх целей Prometheus, источников Grafana и двух алертов. Проверка дашбордов выполняет запросы всех 29 панелей, проверяет наличие числовых значений, фильтрацию CA / market и нормировку плотности. Пустые столбцы и столбцы только с `null` не засчитываются; нулевое значение метрики допустимо.

Для проверки горячей смены модели и переходов обоих алертов в Firing и обратно запустите с хоста (нужен Python 3):

```bash
python3 scripts/check_scenarios.py
```

Сценарий занимает несколько минут, публикует новую модель, временно меняет поток на рискованный, затем останавливает его и возвращает в обычный режим.
